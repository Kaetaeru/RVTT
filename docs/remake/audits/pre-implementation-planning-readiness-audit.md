# 42. 구현 명세 전 기획 완성도 감사

- 상태: 검토용
- 작성일: 2026-08-03
- 목적: 구현 명세와 실제 구현에 들어가기 전에, 현재 기획에서 다시 제품 결정을 요구할 가능성이 높은 항목과 문서 충돌을 식별한다.
- 검토 범위:
  - `AGENTS.md`
  - `docs/remake/README.md`
  - `docs/remake/02`~`41`
  - `ADR-0001`~`ADR-0047`
  - 최근 대화에서 합의했지만 아직 정식 문서가 없는 세션 로비·중도 참여·제어권 배정 결정

## 1. 판정 기준

각 영역을 다음 상태로 분류한다.

```text
READY
→ 구현 명세를 바로 작성할 수 있다.

NEEDS_DEFAULTS
→ 구조는 확정됐지만 기본값·제한값·실패 정책을 결정해야 한다.

NEEDS_PRODUCT_DECISION
→ 사용자 경험이나 규칙 의미가 아직 둘 이상으로 해석된다.

CONFLICT
→ 확정 문서 또는 최신 결정끼리 충돌한다.

MISSING
→ 구현에 필요한 독립 기획이 아직 없다.
```

## 2. 전체 결론

현재 RVTT 기획은 규칙 엔진과 장면 편집의 큰 구조는 충분히 성숙했다. 그러나 바로 전체 구현 명세를 작성하기에는 다음 문제가 남아 있다.

- 문서상 직접 충돌 4건
- 정식 문서가 없는 핵심 제품 흐름 5건
- 구현 중 제품 판단을 다시 요구할 가능성이 높은 항목 17건
- 단순 기본값 확정으로 끝나는 항목 12건

우선 `P0` 항목을 모두 결정하고 기존 문서를 정리한 뒤 공통 구현 아키텍처 명세를 작성해야 한다.

# 3. P0 — 명세 전에 반드시 확정할 항목

## P0-1. 연속 이동과 5피트 논리 격자의 관계

상태: `CONFLICT`

현재 충돌:

```text
AGENTS.md
→ 이동 가능한 표면에는 5피트 × 5피트 논리 겿자가 존재한다.

02-core-session-loop.md
→ 토큰은 연속 좌표로 이동한다.
→ 5피트 격자는 선택적 시각 오버레이다.
```

결정 필요:

1. 내비게이션의 기본 표현도 연속 표면·그래프인가?
2. 내부적으로 5피트 셀을 항상 생성하는가?
3. 범위·점유·거리 계산에서 격자를 사용하는 경우가 있는가?
4. 대각선 이동은 유클리드 거리인가, D&D 격자 규칙인가?

추천:

```text
권위 이동 공간
→ 연속 좌표 + 내비게이션 의미 레이어

5피트 격자
→ 시각 오버레이와 선택적 스냅 보조

거리 계산
→ 기본 유클리드 피트 거리
```

결정 후 `AGENTS.md`, ADR-0006과 이동 관련 문서를 동시에 정정해야 한다.

## P0-2. 전투 중 연속 이동의 확정 단위

상태: `NEEDS_PRODUCT_DECISION`

현재 클릭 이동과 WASD가 같은 검증 시스템을 쓴다는 방향은 확정됐다. 하지만 전투에서 WASD 이동이 어떻게 규칙적으로 확정되는지는 부족하다.

결정 필요:

- 이동 중 경로를 매 순간 확정하는가?
- 일정 거리 단위로 체크포인트를 만드는가?
- 플레이어가 키를 놓았을 때 한 번에 확정하는가?
- 적의 도달거리 이탈, 위험 지형, 준비 행동과 함정은 어느 지점에서 중단되는가?
- 반응창이 열리면 토큰이 즉시 멈추는가?
- 네트워크 지연 중 예측 이동을 어느 정도 허용하는가?
- 이미 이동한 경로를 같은 턴에 되돌아가도 이동력을 다시 소비하는가?

이 항목은 이동, 반응, 함정과 서버 권위가 모두 걸려 있어 구현 중 임의 결정하면 안 된다.

## P0-3. 캠페인 로비·중도 참여·플레이어 배정

상태: `MISSING`

최근 합의한 다음 내용이 아직 정식 ADR과 상세 문서로 없다.

- 캠페인 홈과 세션 대기실
- 실행 중 세션 중도 참여
- 플레이어 한 명당 기본 캐릭터 하나
- DM의 캐릭터·NPC 제어권 배정
- 영구 소유권과 현재 제어권 분리
- 즉시, 행동 종료 후, 턴 종료 후 제어권 변경
- Observer 역할
- 연결 종료 시 임시 제어권 정책
- 세션 종료 시 임시 위임 반환

이 구조는 저장, 권한, HUD, 캐릭터 시트와 재접속에 영향을 주므로 구현 명세 전에 독립 문서가 필요하다.

## P0-4. 플레이어 캐릭터의 영구 소유권 변경 허용 여부

상태: `NEEDS_PRODUCT_DECISION`

기존 결정은 캠페인당 플레이어 캐릭터 하나다. 이후 대화에서는 DM이 캐릭터를 다른 플레이어에게 배정하거나 `Permanent Assignment`할 가능성도 제안됐다.

구분해야 한다.

```text
CharacterOwner
→ 영구 성장·개인 메모·캠페인 귀속 권한

SessionController
→ 현재 세션에서 조작하는 사람
```

결정 필요:

- DM이 플레이어 캐릭터의 영구 Owner를 변경할 수 있는가?
- 아니면 DM 배정은 항상 Controller만 바꾸는가?
- 소유자가 캠페인을 떠났을 때 캐릭터는 캠페인에 남는가?
- 새로운 플레이어에게 기존 캐릭터를 넘길 때 개인 메모와 비공개 정보도 이전되는가?

추천: 초기 버전에서는 플레이어 캐릭터의 영구 소유권 이전은 별도 관리 명령으로 제한하고, 일반 세션 배정은 Controller만 변경한다.

## P0-5. 제품의 초기 지원 기기

상태: `MISSING`

현재 UI와 입력은 사실상 PC 키보드·마우스를 전제로 한다. 그러나 Roblox는 모바일·태블릿·콘솔 사용자도 진입할 수 있다.

결정 필요:

```text
A. 초기 버전은 PC 전용으로 명시
B. 플레이어는 모바일 지원, DM 편집은 PC 전용
C. 모든 기능을 모바일까지 지원
```

이 결정을 하지 않으면 입력 추상화, UI 반응형 범위, Hotbar, 드래그, 우클릭과 단축키 명세가 계속 흔들린다.

추천: 초기 리메이크는 PC 키보드·마우스 우선이며, 모바일은 관전자·기본 플레이만 후속 지원으로 명시한다.

## P0-6. 대화·사회적 상호작용 시스템

상태: `MISSING`

결정 필요:

자동 RPG 대화 트리를 만들 필요는 없더라도, DM이 NPC를 선택하고 발화·판정·핸드아웃을 빠르게 제시하는 흐름은 결정해야 한다.

# 6. 현재 바로 명세 가능한 영역

다음 영역은 위 P0 결정과 독립적으로 구현 명세 작성을 시작할 수 있다.

```text
READY
├─ Grant Graph와 Capability 공통 타입
├─ Trigger, TimingWindow와 UsageGate
├─ EffectRecipe와 PendingEffect
├─ EffectInstance 수명주기
├─ Typed Resource와 휴식 회복 정책
├─ 아이템 정의와 ItemInstance 분리
├─ NPC JSON 검증 파이프라인의 코어
├─ Registry 공통 계약
├─ Result, ErrorCode와 revision 규칙
└─ 서버 권위 Command·CommitGroup 공통 구조
```

다만 실제 기능 구현은 P0 결정 이후에 시작해야 한다. 공통 타입을 먼저 고정해 두면 이후 각 시스템 명세가 일관성을 유지할 수 있다.

# 8. 감사 완료 조건

다음 조건을 만족하면 구현 명세 단계로 넘어간다.

- 모든 P0 항목에 ADR 또는 명시적 결정이 존재한다.
- `AGENTS.md`와 확정 ADR 사이의 충돌이 없다.
- `docs/remake/README.md`가 최신 문서 인덱스를 제공한다.
- 오디오·날씨·모바일 등 초기 범위가 명확하다.
- 캠페인 입장부터 세션 종료까지 사용자 흐름에 빈 구간이 없다.
- 탐험 이동에서 전투 이동으로 넘어가는 규칙이 명확하다.
- 캐릭터 Owner와 Actor Controller의 의미가 고정된다.
- 저장과 턴 롤백에 수치 예산이 있다.
- 각 큰 시스템이 READY 또는 명시적으로 후속 범위로 분류된다.
