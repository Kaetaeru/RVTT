# ADR-0005: 성능, 안정성과 클린코드를 필수 기능으로 취급

- 상태: 확정
- 결정일: 2026-08-03
- 적용 범위: 모든 기획, 구현, 콘텐츠, UI, 저장과 도구

## 배경

RVTT는 장시간 세션에서 여러 토큰, 넓은 3D 장면, 시야, 경로 탐색, 규칙 자동화, VFX와 UI를 동시에 실행한다.

기능이 많아도 프레임 저하, 지연, 저장 실패와 복구하기 어려운 오류가 발생하면 실제 세션에서는 사용할 수 없다. 또한 규칙 콘텐츠가 계속 추가되므로 초기부터 책임 경계가 불명확하거나 중복 코드가 쌓이면 작은 수정이 다른 직업, 주문과 장면을 망가뜨릴 수 있다.

따라서 성능과 유지보수성을 구현 후에 손보는 별도 단계로 두지 않는다.

## 결정

> 최적화, 안정성과 클린코드는 RVTT의 부가 품질이 아니라 모든 기능의 완료 조건이다.

기능은 정상 동작만으로 완료되지 않는다. 다음 조건을 함께 만족해야 한다.

- 장시간 세션에서 지속 가능한 성능
- 실패가 전체 세션으로 전파되지 않는 구조
- 오류 원인과 영향을 빠르게 찾을 수 있는 진단 정보
- 규칙과 콘텐츠를 안전하게 수정할 수 있는 명확한 코드 경계
- 저장과 네트워크 실패에서 복구 가능한 상태 관리
- 테스트와 프로파일링으로 확인된 결과

## 1. 성능 원칙

### 1.1 측정 없는 최적화를 금지한다

성능 문제를 추측만으로 해결하지 않는다.

- 기능별로 CPU, 프레임 시간, 메모리, 네트워크와 인스턴스 수를 측정한다.
- 병목을 프로파일링한 뒤 수정한다.
- 최적화 전후의 측정 결과를 비교한다.
- 성능 개선을 이유로 규칙 정확성과 코드 이해 가능성을 불필요하게 훼손하지 않는다.

### 1.2 성능 예산을 가진다

구현 단계에서 기준 장면과 기준 기기를 정하고 다음 예산을 관리한다.

- 클라이언트 프레임 시간
- 서버 프레임과 스크립트 시간
- 장면 인스턴스 수
- 메모리 사용량과 증가 추세
- 초당 네트워크 송수신량
- Remote 호출 빈도와 페이로드 크기
- 경로 탐색 응답 시간
- 씬 로딩과 전환 시간
- 저장 시간

초기 목표는 데스크톱 기준으로 부드러운 60 FPS를 지향한다. 정확한 기준 기기, 허용 하한과 장면 규모는 성능 예산 문서에서 별도로 고정한다.

### 1.3 전체 장면을 매 프레임 순회하지 않는다

다음 구현을 금지한다.

- 모든 토큰과 오브젝트를 매 프레임 검사
- 모든 격자 셀에 Part, Script 또는 연결 이벤트 생성
- 상태 변화가 없는데 반복 폴링
- 매 프레임 대량 Raycast와 경로 탐색
- UI가 닫혀 있어도 계속 갱신
- 동일 데이터를 모든 클라이언트에 반복 전송

대신 다음을 우선한다.

- 이벤트 기반 갱신
- 공간 인덱스와 영역 질의
- 변경된 데이터만 전송하는 델타 동기화
- 거리와 가시성 기반 활성화
- 스트리밍, 컬링과 LOD
- 오브젝트 풀링
- 계산 결과 캐시와 명확한 무효화
- 장면 공개 전 내비게이션과 정적 데이터 사전 계산

### 1.4 격자와 경로 탐색

5피트 격자는 논리 데이터다.

- 화면에 보이는 셀만 시각화한다.
- 정적 이동 가능 표면은 씬 게시 시 계산한다.
- 문, 장애물과 위험 지대 같은 동적 변경만 런타임에 반영한다.
- 클릭 이동과 WASD 이동은 같은 경로 및 검증 시스템을 사용한다.
- 목적지가 바뀌거나 이동 가능 상태가 변할 때만 경로를 다시 계산한다.
- 전체 맵 경로를 불필요하게 매 프레임 갱신하지 않는다.

### 1.5 클라이언트와 서버의 책임

클라이언트는 다음을 담당한다.

- 카메라
- 입력
- 이동과 범위 미리보기
- 로컬 UI
- 서버가 승인한 결과의 부드러운 연출

서버는 다음을 담당한다.

- 권한과 소유권
- 확정 위치
- 이동 비용
- 규칙 판정
- 캐릭터와 전투 상태
- 저장

서버가 모든 시각 연출을 직접 복제하거나 클라이언트가 권위 상태를 임의로 확정하지 않는다.

## 2. 클린코드 원칙

### 2.1 책임을 작게 나눈다

하나의 모듈이 다음을 모두 처리하지 않는다.

- 입력
- UI
- 네트워크
- 규칙 판정
- 저장
- VFX

각 모듈은 이름으로 설명할 수 있는 하나의 중심 책임을 가진다.

### 2.2 규칙 계산은 가능한 한 순수하게 만든다

명중 보너스, 이동 비용, 주문 DC와 피해식 같은 계산은 Roblox 인스턴스와 UI에 직접 의존하지 않는 함수로 분리한다.

동일한 입력에는 동일한 결과가 나와야 하며, 단위 테스트가 가능해야 한다.

### 2.3 명시적인 의존성

- 숨겨진 전역 상태를 사용하지 않는다.
- 임의의 싱글턴 접근을 남용하지 않는다.
- 필요한 서비스와 레지스트리는 명시적으로 전달한다.
- 순환 의존성을 만들지 않는다.
- 출처 팩이 코어 내부 경로를 임의로 참조하지 않는다.

### 2.4 타입과 계약

Luau 타입을 적극적으로 사용한다.

- 공개 함수의 입력과 반환 타입을 명시한다.
- 직렬화 데이터와 런타임 객체 타입을 구분한다.
- Remote 입력은 스키마 검증을 거친다.
- `any`와 무분별한 타입 단언을 피한다.
- nil 가능성과 실패 결과를 호출자가 처리하도록 만든다.

가능한 모듈은 strict 타입 검사를 목표로 한다.

### 2.5 이름과 상수

- 한국어 표시 문자열을 코드 식별자로 사용하지 않는다.
- 콘텐츠 ID, 오류 코드와 이벤트 이름은 중앙 정의를 사용한다.
- 의미를 알 수 없는 숫자와 문자열을 직접 넣지 않는다.
- 함수와 변수 이름은 역할과 단위를 드러낸다.
- 설명이 필요한 복잡한 코드보다 구조 자체가 의도를 보여야 한다.

### 2.6 중복보다 공통 계약

같은 규칙을 여러 주문과 특성에 복사하지 않는다. 공통 엔진과 계약을 사용한다.

다만 차이가 큰 콘텐츠를 하나의 거대한 조건문에 억지로 넣지 않는다. 콘텐츠 고유 예외는 전용 모듈에 둔다.

## 3. 오류 처리와 진단

### 3.1 오류를 삼키지 않는다

`pcall`로 오류를 숨기고 아무 일도 없었던 것처럼 계속하지 않는다.

복구 가능한 실패와 개발 오류를 구분한다.

- 복구 가능한 실패는 구조화된 실패 결과를 반환한다.
- 예상하지 못한 오류는 컨텍스트와 함께 기록한다.
- 사용자에게는 이해 가능한 메시지를 표시한다.
- 서버 상태가 부분 적용되었다면 롤백하거나 안전한 상태로 전환한다.

### 3.2 구조화된 로그

오류와 중요한 상태 변경에는 가능한 범위에서 다음 정보를 포함한다.

- 오류 코드
- 기능과 모듈 이름
- actorId 또는 tokenId
- contentId
- sourcePack과 version
- campaignId, sceneId와 sessionId
- 현재 플레이 모드와 턴
- 요청한 플레이어
- 관련 명령 또는 실행 ID

비밀번호, 개인 정보와 불필요한 전체 저장 데이터는 로그에 남기지 않는다.

### 3.3 콘텐츠 오류 격리

하나의 주문, 특성, 몬스터 능력 또는 VFX 오류가 전체 전투 루프와 세션을 중단시키지 않게 한다.

- 출처 팩 로딩 시 콘텐츠 정의를 검증한다.
- 잘못된 콘텐츠는 비활성화하고 원인을 표시한다.
- 실행 중 실패하면 해당 실행을 안전하게 취소한다.
- 이미 소비한 자원과 적용한 상태는 원자적으로 처리하거나 되돌린다.

### 3.4 시간 제한과 취소

Remote 응답, 데이터 로딩, 저장과 비동기 작업은 무한히 기다리지 않는다.

- 타임아웃을 둔다.
- 취소 가능한 작업은 취소 토큰 또는 실행 상태를 가진다.
- 씬 전환과 세션 종료는 진행 중 작업을 정리한다.

## 4. 상태와 저장 안정성

- 저장 데이터는 스키마 버전을 가진다.
- 스키마 변경에는 마이그레이션이 필요하다.
- 레벨업, 장비 변경과 보상 지급은 부분 적용되지 않게 한다.
- 반복 요청이 중복 보상과 중복 소비를 만들지 않게 한다.
- 재접속 시 서버의 권위 상태에서 복구한다.
- 저장 실패를 성공으로 표시하지 않는다.
- 자동 저장과 명시적 저장의 충돌을 제어한다.

## 5. 테스트와 검증

### 필수 검증 범위

변경 성격에 따라 다음을 확인한다.

- 정상 사용 흐름
- 권한이 없는 요청
- 잘못된 대상과 범위
- 자원 부족
- 중복 요청
- 네트워크 지연과 순서 변경
- 플레이어 이탈과 재접속
- 씬 전환과 세션 종료
- 저장 실패와 마이그레이션
- 다수 토큰과 큰 장면에서의 성능
- 장시간 실행 후 메모리 증가

### 자동화 우선 영역

- 규칙 계산
- 파생 능력치
- 경로 비용
- 콘텐츠 정의 검증
- 캐릭터 생성과 레벨업 검증
- 직렬화와 마이그레이션
- 상태 효과 수명
- 행동 경제

## 6. 완료 조건

기능은 다음이 확인되어야 완료다.

1. 기획과 ADR의 요구사항을 충족한다.
2. 서버 권한과 잘못된 요청 검증이 있다.
3. 정상 흐름과 주요 실패 흐름을 확인했다.
4. 저장과 재접속 영향을 확인했다.
5. 한국어 번역 키가 준비되었다.
6. 프로파일링 결과 허용할 수 없는 병목이 없다.
7. 장시간 유지되는 연결, 이벤트와 인스턴스가 정리된다.
8. 오류가 발생했을 때 원인을 찾을 로그와 컨텍스트가 있다.
9. 코드 책임과 의존성이 설명 가능하다.
10. 남은 제한을 명시했다.

## 7. 금지 사항

- 기능을 빠르게 끝내기 위해 서버 검증 생략
- 오류를 숨기기 위한 빈 `pcall`
- 거대한 범용 관리자 하나에 모든 책임 추가
- 임시 코드를 설명 없이 영구 구조로 남김
- 같은 규칙 로직 복사
- 무제한 루프, 연결과 태스크 방치
- 성능 측정 없이 "최적화됨"이라고 보고
- 테스트 없이 "오류 없음"이라고 보고
- 프레임 저하를 VFX와 UI의 당연한 비용으로 취급
- 깨진 저장 데이터와 콘텐츠를 조용히 무시

## 결과

성능과 유지보수성 때문에 기능 개발 속도가 잠시 느려질 수 있다. 대신 기능이 늘어날수록 수정 비용과 세션 장애가 폭발하는 상황을 방지한다.

모든 에이전트와 구현 작업은 이 결정을 기능 명세와 동일한 강도로 적용해야 한다.
