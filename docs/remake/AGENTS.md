# RVTT Remake Documentation Agent Rules

이 문서는 `docs/remake/` 아래에서 기획, 구현명세와 결정 문서를 작성하거나 수정하는 모든 에이전트가 따라야 하는 경로별 규약이다.

저장소 루트의 [`AGENTS.md`](../../AGENTS.md)를 대체하지 않고 보충한다. 두 문서가 충돌하면 루트 `AGENTS.md`와 확정 ADR의 우선순위를 따른다.

---

## 1. 구현명세의 역할

구현명세는 제품 기획을 다시 논의하는 문서도, 코드를 미리 길게 적어 두는 문서도 아니다.

구현명세의 역할은 다음과 같다.

```text
확정된 기획과 ADR
→ 구현 가능한 상태·데이터·명령·모듈 계약
→ 독립적으로 검증 가능한 구현 단계
→ 테스트와 완료 판정
```

구현 에이전트가 중요한 동작을 추측하지 않고 작업할 수 있어야 한다.

구현명세에서 새로운 제품 방향이나 되돌리기 어려운 아키텍처 결정을 몰래 확정하지 않는다. 그런 결정이 필요하면 먼저 ADR 또는 관련 기획 문서에 기록한다.

---

## 2. 언제 구현명세가 필요한가

다음 중 하나라도 해당하면 프로덕션 구현 전에 구현명세를 작성한다.

- 서버와 클라이언트가 함께 변경됨
- Remote, 명령 또는 권한 검증이 추가됨
- 영구 저장 데이터나 마이그레이션이 변경됨
- 여러 서비스 또는 모듈 사이의 새 계약이 생김
- 사용자가 거치는 상태 전이가 두 단계 이상임
- 실행 취소, 재시도, 중복 요청 또는 롤백이 필요함
- 성능 예산이나 장시간 세션 안정성에 영향을 줌
- 다른 기능이 확장점으로 사용할 공통 기반을 만듦
- 구현 범위가 한 파일의 명백한 수정으로 설명되지 않음

문구 수정, 단순 번역 수정과 명백한 국소 버그 수정에는 별도 구현명세를 강제하지 않는다. 다만 저장, 보안 또는 규칙 결과가 달라지면 작은 변경이라도 명세 또는 ADR 근거가 필요하다.

---

## 3. 명세의 크기와 경계

### 수직 단위 하나를 명세 하나로 만든다

구현명세는 파일 하나가 아니라 **사용자가 확인할 수 있는 결과 하나**를 기준으로 나눈다.

좋은 예:

```text
프리팹 선택
→ 로컬 고스트 미리보기
→ 서버 배치 검증
→ 씬 원본과 Workspace 생성
→ 실행 취소
→ 저장과 재접속 복구
```

나쁜 예:

```text
클라이언트 코드 전부
서버 코드 전부
씬 편집기 전체
UI 서비스 만들기
```

한 명세는 독립적으로 구현, 리뷰, 테스트하고 실패 시 되돌릴 수 있어야 한다.

### 범위가 너무 크면 분할한다

다음 징후가 있으면 여러 수직 명세로 나눈다.

- 서로 독립적인 사용자 결과가 여러 개임
- 완료 여부를 하나의 테스트 흐름으로 확인할 수 없음
- 일부만 배포하거나 되돌릴 수 없음
- 미결정 사항 하나가 문서 대부분을 막음
- 첫 단계가 끝나기 전까지 실행 가능한 결과가 전혀 없음

분할된 명세는 공통 기반 명세와 기능 명세의 의존성을 명시한다.

---

## 4. 작성 전 조사

구현명세는 저장소를 조사한 뒤 작성한다.

반드시 확인한다.

1. 관련 확정 ADR과 기획 문서
2. 현재 브랜치와 변경 중인 파일
3. 같은 책임을 가진 기존 서비스와 모듈
4. 기존 타입, ID, Registry, Remote와 오류 코드
5. 저장 스키마와 마이그레이션
6. 기존 테스트, 진단과 성능 측정 경로
7. 제거하거나 대체될 구형 흐름

조사하지 않은 파일 경로, 서비스 이름과 API를 사실처럼 적지 않는다.

아직 존재하지 않는 구조는 `신규 제안`으로 명시하고, 기존 구조와 왜 통합할 수 없는지 설명한다.

---

## 5. 구현명세 파일 규칙

기본 위치:

```text
docs/remake/specs/<영역>/<번호>-<기능명>.md
```

예시:

```text
docs/remake/specs/scene-editor/001-prefab-placement.md
docs/remake/specs/combat/003-action-resolution.md
```

파일 상단에 다음 메타데이터를 둔다.

```markdown
# 구현명세: 기능 이름

- 상태: 초안 | 준비 완료 | 구현 중 | 검증 완료 | 대체됨
- 관련 기획:
- 관련 ADR:
- 선행 명세:
- 후속 명세:
- 영향 영역:
```

상태 의미:

- `초안`: 결정이나 계약이 부족해 구현 착수 불가
- `준비 완료`: 아래 준비 완료 게이트를 모두 통과
- `구현 중`: 명세에 따라 프로덕션 작업 진행 중
- `검증 완료`: 완료 기준과 테스트 증거가 확인됨
- `대체됨`: 새로운 명세나 ADR이 대신함

문서의 상태를 실제 진행보다 앞서 표시하지 않는다.

---

## 6. 필수 구현명세 구조

아래 절은 해당 기능과 무관한 경우에만 `해당 없음`과 이유를 적고 생략할 수 있다.

### 6.1 목표와 사용자 결과

- 사용자가 무엇을 할 수 있게 되는가
- 완료 후 화면과 게임 상태에서 무엇이 달라지는가
- 한두 문장으로 성공 결과를 설명한다

내부 모듈 이름을 목표로 쓰지 않는다.

### 6.2 범위와 비범위

- 이번 명세에서 끝까지 구현할 범위
- 의도적으로 하지 않는 범위
- 후속 명세로 넘기는 항목

`나중에 처리`만 적지 말고 어느 경계까지 정상 지원하는지 명시한다.

### 6.3 근거와 추적성

각 핵심 요구가 어느 기획 또는 ADR에서 왔는지 연결한다.

```text
요구사항
→ 근거 문서와 절
→ 구현 계약
→ 검증 항목
```

명세가 ADR을 재해석하거나 약화하지 않는다.

### 6.4 현재 구조 조사

- 관련된 실제 파일과 현재 책임
- 재사용할 기존 타입과 서비스
- 대체하거나 제거할 경로
- 호환성을 유지해야 할 호출자

파일 목록만 나열하지 말고 변경 이유와 책임을 한 줄씩 적는다.

### 6.5 사용자 흐름과 상태 전이

정상 흐름을 입력부터 확정 결과까지 순서대로 적는다.

상태가 있다면 상태명과 허용 전이를 정의한다.

```text
Idle
→ Previewing
→ ConfirmPending
→ Committed

Previewing
→ Cancel
→ Idle
```

취소, 재시도, 화면 전환, 사용자 이탈과 세션 종료 흐름도 포함한다.

### 6.6 권한과 책임 분리

클라이언트, 서버, Shared, 저장 계층과 DM 중 누가 무엇을 소유하는지 표 또는 목록으로 정의한다.

반드시 명시한다.

- 클라이언트가 미리 볼 수 있는 값
- 서버가 재계산하거나 검증할 값
- 서버만 변경할 수 있는 상태
- DM 승인 지점
- 저장 원본과 런타임 파생 상태

`서버가 검증한다`로 끝내지 말고 검증 항목을 열거한다.

### 6.7 데이터와 타입 계약

공개 계약을 구현 전에 정의한다.

- 고정 ID와 이름 규칙
- 직렬화 타입
- 런타임 타입
- 필수·선택 필드
- 기본값과 nil 의미
- 좌표, 거리, 시간과 수치 단위
- 버전 필드
- 이전 데이터와의 호환 방식

직렬화 데이터와 Roblox Instance 참조를 섞지 않는다.

필요한 경우 최소한의 typed Luau 형태로 표현하되, 실제 구현 전체를 문서에 복사하지 않는다.

### 6.8 명령과 네트워크 계약

Remote 또는 명령마다 다음을 정의한다.

- 명령 ID
- 요청자와 필요한 권한
- 요청 스키마와 크기 제한
- 서버 검증 순서
- 성공 결과
- 구조화된 실패 코드
- 중복 실행 ID와 멱등성
- 요청 빈도 제한
- 클라이언트 예측과 서버 보정 방식

클라이언트가 생성한 Instance와 판정 결과를 서버가 신뢰하지 않는다.

### 6.9 모듈과 파일 책임

변경하거나 추가할 파일을 구현 순서가 아니라 책임 경계로 정리한다.

각 항목에는 다음을 적는다.

```text
경로
→ 책임
→ 공개 계약
→ 의존 대상
→ 소유하지 않는 책임
```

하나의 거대한 Manager에 기능을 계속 추가하지 않는다.

중앙 Registry 또는 공통 호스트가 있다면 신규 기능이 등록만으로 연결되는지 확인한다.

### 6.10 저장과 마이그레이션

- 저장되는 원본과 저장하지 않는 파생값
- 스키마 버전
- 기존 데이터 마이그레이션
- 반복 실행 안전성
- 저장 실패 시 상태
- 자동 저장과 명시적 저장 충돌
- 재접속과 씬 재로딩 복구

저장 영향이 없다면 왜 없는지 적는다.

### 6.11 UI, 입력과 현지화

- 화면에서 보이는 상태와 피드백
- 입력 문맥과 Q·E 등 공통 입력 의미
- 텍스트 입력 중 단축키 차단
- 로딩, 비활성, 실패와 권한 없음 상태
- 번역 키와 변수
- 패널, 인스펙터 또는 툴 모듈 확장점

사용자용 문자열을 코드 상수로 명세하지 않는다.

### 6.12 실패, 동시성, 취소와 롤백

최소한 다음을 검토한다.

- 권한 없음
- 잘못되거나 오래된 대상
- 중복 또는 순서가 바뀐 요청
- 네트워크 지연
- 작업 중 씬 또는 턴 변경
- 사용자 이탈
- 저장 실패
- 일부 단계만 성공한 경우
- 모듈 오류와 안전한 비활성화

실패 후 남아야 하는 안전 상태를 명시한다.

### 6.13 성능과 생명주기

측정할 항목과 위험한 반복 작업을 정한다.

- 프레임당 실행 여부
- 이벤트 기반 갱신 지점
- 공간 질의와 캐시
- 네트워크 빈도와 payload 크기
- 생성되는 Instance 수
- 연결, 태스크, 고스트와 임시 객체 정리
- 씬 전환과 모드 종료 시 해제
- 기준 장면과 측정 방법

`최적화한다`가 아니라 측정 가능한 기준을 적는다. 아직 수치가 없으면 무엇을 측정해 기준을 확정할지 적는다.

### 6.14 진단과 로그

- 중요한 명령과 상태 전이
- 오류 코드
- 필요한 sceneId, objectId, actorId와 commandId
- 사용자에게 보여 줄 메시지
- 개발 로그와 사용자 메시지의 분리

전체 저장 데이터와 민감 정보를 로그에 넣지 않는다.

### 6.15 구현 순서

구현 단계는 각 단계가 끝날 때 저장소가 실행 가능하고 검증 가능하도록 나눈다.

각 단계마다 다음 형식을 사용한다.

```text
단계 목표:
변경 책임:
선행 조건:
완성되는 실제 흐름:
검증 방법:
실패 시 안전 상태:
완료 기준:
```

공통 타입만 대량으로 만들고 실제 흐름이 마지막까지 작동하지 않는 수평 구현을 피한다.

가능한 한 가장 얇은 end-to-end 흐름을 먼저 완성하고, 이후 기능과 예외를 확장한다.

### 6.16 테스트 계획

요구사항과 테스트를 연결한다.

최소 범주:

- 정상 흐름
- 취소와 되돌리기
- 잘못된 입력
- 권한 없는 요청
- 중복 요청
- 네트워크 지연과 순서 변경
- 사용자 이탈과 재접속
- 씬 또는 모드 전환
- 저장과 마이그레이션
- 장시간 실행과 자원 정리
- 기준 장면 성능

각 테스트에 자동화, 수동 또는 프로파일링 여부를 표시한다.

실행 환경이 없어 검증할 수 없는 항목은 검증한 것으로 표시하지 않는다.

### 6.17 완료 기준

완료 기준은 관찰 가능하고 참·거짓으로 판정할 수 있어야 한다.

나쁜 예:

```text
배치가 잘 작동한다.
오류를 적절히 처리한다.
성능이 좋다.
```

좋은 예:

```text
등록되지 않은 PrefabId 요청은 Workspace와 씬 원본을 변경하지 않고
PREFAB_NOT_REGISTERED 실패 코드를 반환한다.
```

각 완료 기준은 하나 이상의 테스트 또는 측정 항목과 연결한다.

### 6.18 미결정 사항과 위험

- 구현을 막는 결정
- 구현 중 확인 가능한 가정
- 외부 의존성
- 성능과 마이그레이션 위험
- 후속 명세로 넘긴 항목

확정되지 않은 내용을 본문에 확정 사실처럼 섞지 않는다.

---

## 7. 준비 완료 게이트

다음 조건을 모두 충족해야 상태를 `준비 완료`로 변경하고 프로덕션 구현을 시작할 수 있다.

1. 사용자 결과와 비범위가 명확함
2. 관련 ADR과 기획 근거가 연결됨
3. 실제 기존 파일과 계약을 조사함
4. 정상 흐름과 주요 상태 전이가 정의됨
5. 클라이언트와 서버의 권한 경계가 정의됨
6. 데이터, ID, 단위와 버전 계약이 정의됨
7. 명령과 실패 코드가 정의됨
8. 저장과 마이그레이션 영향이 정의됨
9. 취소, 중복 요청과 부분 실패의 안전 상태가 정의됨
10. 단계별 구현 결과가 각각 검증 가능함
11. 테스트와 성능 측정 방법이 존재함
12. 완료 기준이 관찰 가능함
13. 구현 방향을 바꿀 중대한 제품 결정이 미해결 상태가 아님

하나라도 충족하지 못하면 `초안` 상태를 유지한다.

미결정 사항이 구현 결과와 저장 호환성에 영향을 주지 않는 사소한 표현 문제라면 명시적 가정으로 진행할 수 있다. 권한, 데이터 원본, 사용자 흐름 또는 공개 계약을 바꾸는 문제라면 임의로 정하지 않는다.

---

## 8. 구현 중 명세 관리

구현명세는 구현 시작 후 버리는 문서가 아니다.

- 코드 조사 결과가 명세와 다르면 명세를 먼저 또는 같은 변경에서 수정한다.
- 구현 편의를 위해 계약을 조용히 바꾸지 않는다.
- 예상하지 못한 제품 결정이 필요하면 ADR 또는 기획으로 되돌린다.
- 완료된 단계와 검증 증거를 문서에 표시한다.
- 파일 경로와 타입 이름이 확정되면 제안 표기를 실제 값으로 갱신한다.
- 제거된 범위와 후속 작업을 남긴다.

코드와 명세가 불일치한 상태를 정상적인 완료로 보고하지 않는다.

---

## 9. 효율적인 작성 원칙

### 계약에 집중한다

코드로 쉽게 읽을 수 있는 내부 구현을 문서에 장황하게 복사하지 않는다.

다음은 자세히 적는다.

- 책임 경계
- 상태 전이
- 데이터와 명령 계약
- 실패와 롤백
- 성능 위험
- 검증 기준

다음은 필요 이상으로 적지 않는다.

- 자명한 getter와 setter
- 모든 비공개 함수 이름
- 확정되지 않은 폴더 구조
- 일반적인 Luau 문법
- UI 픽셀 단위 세부사항

### 한 문장은 하나의 검증 가능한 주장으로 쓴다

`적절히`, `필요한 경우`, `안전하게`, `효율적으로` 같은 표현만으로 요구사항을 끝내지 않는다.

조건, 결과와 실패 상태를 함께 적는다.

### 예시는 계약을 명확하게 할 때만 쓴다

예시 데이터는 실제 ID 규칙과 단위를 따른다.

예시가 규칙인지 단순 설명인지 구분한다.

### 미래 확장은 확장점까지만 정의한다

확실하지 않은 미래 기능을 미리 구현하도록 명세하지 않는다.

대신 다음만 보장한다.

- 공개 Registry 또는 인터페이스
- 버전 계약
- 의존성 방향
- 기존 코드를 수정하지 않고 추가할 수 있는 등록 지점

## 10. 기능별 추가 체크리스트

### 씬 편집 도구 모듈

도구 모듈 명세에는 추가로 다음을 포함한다.

- 고유 Tool ID와 버전
- capabilities와 dependencies
- 활성화·작업·확정·취소·비활성화 생명주기
- 가상 커서, 고스트와 스냅 사용 방식
- 인스펙터 필드와 패널 등록
- 서버 명령과 오브젝트 타입
- 직렬화 데이터와 마이그레이션
- 실행 취소 명령
- ViewY와 선택 판정
- 종료 시 연결과 임시 객체 정리
- 모듈 실패 격리

모듈이 물리 키, RemoteEvent, Workspace 변경과 독자적인 실행 이력을 직접 소유하지 않게 한다.

### 규칙 콘텐츠

주문, 특성, 아이템과 몬스터 능력 명세에는 추가로 다음을 포함한다.

- 콘텐츠 ID, 규칙 세트와 출처 팩
- `Executable`, `Guided` 또는 `Assisted` 수준
- 사용 시점과 행동 경제
- 대상, 사거리와 시야
- 자원 소비와 회복
- 판정, 효과와 지속시간
- 집중, 중첩과 충돌
- DM 승인 지점
- 시트, 행동 UI, 로그와 번역
- 저장과 재접속

### 영구 데이터 변경

저장 명세에는 추가로 다음을 포함한다.

- 이전·새 스키마 예시
- 버전 상승 규칙
- 멱등 마이그레이션
- 손상 데이터 처리
- 부분 저장 실패
- 롤백 또는 이전 버전 호환 전략
- 재접속 검증

## 11. 금지되는 구현명세 패턴

- 저장소 조사 없이 만든 가상의 파일 목록
- `Manager` 하나가 모든 책임을 갖는 구조
- 정상 흐름만 있고 취소와 실패 흐름이 없음
- `서버에서 검증`처럼 검증 항목이 없는 문장
- `오류 처리`, `최적화`, `테스트 추가`만 적은 항목
- 모델 전체를 코드 예제로 복사하고 공개 계약은 빠뜨림
- 현재 범위와 미래 아이디어를 한 명세에 혼합
- ADR이 필요한 결정을 구현명세에서 확정
- 모든 기능을 끝내야 첫 테스트가 가능한 구현 순서
- 실행할 수 없는 테스트를 완료 조건으로 표시
- 코드와 다른 명세를 수정하지 않고 방치
- TODO를 숨긴 채 상태를 `준비 완료` 또는 `검증 완료`로 변경
